# VPS 测量与默认容量

2026-10-19，在用户的 Oracle VPS 原机测量：aarch64、2 个 CPU、11.65 GiB RAM；开始测量时约 9.94 GiB 可用，未配置 swap。使用独立 `/tmp/echo-bench.*` 目录和 Docker 容器，没有更改原有应用。运行容器限制为 2 CPU / 2 GiB；Rust 1.96 release 构建。

## 单个求解器

程序：`cargo run --release -p echo_app --example profile -- joint 7`。每个组合独立启动进程：先冷求解，再查询同一策略 100 次。采用线性评分，目标 70，默认成本；5 个有效权重使用应用默认配置，7 个加入生命与小生命权重（非角色预设）。强化、联合查询新胚子；重抽查询合法的五条最低档副词条。下表是单轮实测，不是所有预设的最坏上限。

| 有效权重数 | 模式 | 冷求解 ms | 热查询均值 ms | 峰值 RSS MiB | 策略分配容量 MiB |
| --- | --- | ---: | ---: | ---: | ---: |
| 5 | 强化 | 158 | 0.002 | 53.9 | 40.3 |
| 5 | 重抽 | 86 | 0.330 | 8.3 | 4.9 |
| 5 | 联合 | 174 | 0.002 | 9.7 | 6.3 |
| 7 | 强化 | 300 | 0.002 | 64.3 | 43.5 |
| 7 | 重抽 | 1400 | 2.962 | 72.1 | 56.0 |
| 7 | 联合 | 2275 | 0.002 | 78.3 | 62.7 |
| 9 | 强化 | 667 | 0.002 | 78.2 | 57.1 |
| 13 | 强化 | 2386 | 0.002 | 99.8 | 82.7 |

9 和 13 个有效权重的重抽／联合，在状态分配前分别因约 246 万、2730 万状态而被默认 75 万上限拒绝（约 0.03 ms）。这不是成功求解性能数据。不同评分会合并不同数值档位，不能仅凭非零权重数量预测容量。

峰值来自 Linux `/proc/self/status` 的 VmHWM；分配容量来自 solver 的 Vec capacity 求和，不包含分配器和临时缓冲区。冷热耗时由应用内计时，不含浏览器网络往返。

## 默认选择

- 保留 512 MiB 策略缓存，实际分配容量再乘 1.25 计入；最多 32 条。
- 同时只冷构建 1 份策略，另有 2 个缓存查询工作名额。冷构建不会占住所有缓存查询。
- 2 GiB 容器／systemd 硬上限，给构建临时内存与分配器留空间。缓存预算不是 RSS 限制；释放 Vec 后 RSS 也不保证立即下降。
- 最多 8 个不同配置等待／正在构建，64 个任务和结果，每个普通 IP 最多 2 个未完成任务。
- 每 IP 每小时新建强化／重抽／联合分别 60／12／4 次；每分钟 240 个预览和求解请求。共享缓存和相同配置的正在进行的求解不重复扣小时额度。

这些测量支持先从较小的内存预算起步；不能据此承诺任意评分配置都能完成。提高状态或转移上限之前，应重新测量最大允许配置。管理员访问密钥只绕过个人配额，全局保护仍生效。

## HTTP 多人验证

同一台 VPS、同样的 2 CPU / 2 GiB 隔离容器运行 `python3 scripts/test-server-http.py target/release/echo_server`（容器内使用上传的同名脚本）。5 个模拟 IP 提交相同配置，并验证结果归属、小时额度、伪造转发前缀不能绕过额度、无效密钥拒绝、有效密钥绕过额度。

随后启动 7 个有效权重的联合冷求解，同时完成 50 次已有策略查询。提交和取得任务结果的完整 HTTP 往返：中位数 **1.01 ms**、P95 **1.13 ms**。服务进程 VmHWM **95.7 MiB**、测试末 VmRSS **86.2 MiB**。这是容器内 loopback 测量，**不含公网 RTT、反向代理和浏览器轮询等待**，不能当成终端用户响应时间。全部断言通过；本地真实 Chromium 三模式回归与访问密钥流程也通过。
