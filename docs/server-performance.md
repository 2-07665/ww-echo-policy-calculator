# 服务器性能测量

本文记录[部署指南](deployment.md)中默认容量参数的测量依据。

## 测量环境

- 时间：2026-10-19
- 机器：Oracle VPS，aarch64，2 CPU，11.65 GiB 内存，无 swap
- 运行限制：Docker 容器，2 CPU / 2 GiB 内存
- 构建：Rust 1.96，release

测量使用独立的临时目录和容器，没有改动原有应用。

## 单次求解

命令：`cargo run --release -p echo_app --example profile -- <模式> <有效权重数>`

每组参数单独启动一个进程，先冷求解一次，再对同一策略查询 100 次。评分为线性评分，目标 70 分，资源价值取默认值。

- 5 个有效权重：应用默认配置；
- 7 个有效权重：在默认配置上加入生命和小生命（并非某个角色预设）。

强化和联合模式查询新胚子，重抽模式查询五条全是最低档的声骸。

| 有效权重数 | 模式 | 冷求解 (ms) | 查询均值 (ms) | 峰值内存 (MiB) | 策略占用 (MiB) |
|---:|---|---:|---:|---:|---:|
| 5 | 强化 | 158 | 0.002 | 53.9 | 40.3 |
| 5 | 重抽 | 86 | 0.330 | 8.3 | 4.9 |
| 5 | 联合 | 174 | 0.002 | 9.7 | 6.3 |
| 7 | 强化 | 300 | 0.002 | 64.3 | 43.5 |
| 7 | 重抽 | 1400 | 2.962 | 72.1 | 56.0 |
| 7 | 联合 | 2275 | 0.002 | 78.3 | 62.7 |
| 9 | 强化 | 667 | 0.002 | 78.2 | 57.1 |
| 13 | 强化 | 2386 | 0.002 | 99.8 | 82.7 |

- **峰值内存**：Linux `/proc/self/status` 中的 VmHWM。
- **策略占用**：求解器各数组已分配容量之和，不含分配器开销和临时缓冲区。服务端缓存按这个数值的 1.25 倍计入预算。
- 耗时由程序内部计时，不含网络往返。

有效权重为 9 和 13 时，重抽和联合模式的状态数分别约为 246 万和 2730 万，超过默认的 75 万上限，在分配内存前即被拒绝（约 0.03 ms），因此表中没有这几行。

以上是单轮测量结果，不代表所有预设下的最坏情况。不同评分会合并不同的数值档位，仅凭有效权重的个数无法准确预测规模。

## HTTP 多用户测试

在同一台 VPS 上，以相同的 2 CPU / 2 GiB 容器运行 `scripts/test-server-http.py`。测试模拟 5 个 IP 提交相同配置，验证了以下几点：结果只返回给提交者、小时额度生效、伪造的转发头无法绕过额度、无效密钥被拒绝、有效密钥可以绕过额度。全部断言通过。

随后在一份 7 个有效权重的联合冷求解进行期间，完成 50 次已有策略的查询：

| 指标 | 数值 |
|---|---|
| 提交到取得结果的往返时间，中位数 | 1.01 ms |
| 同上，P95 | 1.13 ms |
| 服务进程峰值内存 (VmHWM) | 95.7 MiB |
| 测试结束时内存 (VmRSS) | 86.2 MiB |

这是容器内的本机回环测量，**不包含**公网延迟、反向代理和浏览器轮询的等待时间，不能当作用户实际感受到的响应时间。

## 由此确定的默认值

- 策略缓存 512 MiB，最多 32 条；
- 同一时间只冷求解 1 份策略，另留 2 个名额给缓存查询；
- 容器和 systemd 的硬内存上限为 2 GiB，为计算时的临时内存和分配器留出余量；
- 最多 8 个不同配置排队或计算中，64 个任务，每个普通 IP 最多 2 个未完成任务；
- 每 IP 每小时新建强化 / 重抽 / 联合策略各 60 / 12 / 4 次，每分钟最多 240 次请求。

测量结果说明，从较小的内存预算起步是可行的，但不能保证任意评分配置都能完成求解。提高状态或转移上限之前，应针对允许的最大配置重新测量。
